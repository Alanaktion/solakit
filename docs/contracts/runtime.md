# Runtime records, configuration, and resource ownership

Phase 2 contract, implemented on 2026-11-16. Core modules are
[`records.py`](../../src/solakit/records.py), [`config.py`](../../src/solakit/config.py),
and [`runtime.py`](../../src/solakit/runtime.py). None imports HTTP or provider SDK
types. Pydantic validates owned values; it is not an application container.
Phase 3 [storage](storage.md) now persists these values and supplies durable
admission/evidence. Phase 4 [model requests](model-prompts.md) add exact private
request artifacts and a pinned oMLX adapter. Phase 5 [tool dispatch](tools.md) enforces saved/current authority and guarded
services; scheduling and the model/tool cycle retain their later phase gates. An in-memory transition alone is not a durable admission or effect receipt.

## Records and identities

Every record has `schema_version = 1`, `id`, `created_at`, and `origin`. IDs are
exactly 32 lowercase hexadecimal characters, generated with UUID4; validate before
using them as path components. They are opaque identities, not paths. All recorded
timestamps must be aware UTC and serialize as ISO 8601 with `Z`. Unknown fields,
wrong types, unsupported versions, nonfinite JSON numbers, naive times, and non-UTC
offsets fail validation.
Use `model_validate_json` for serialized JSON (including enums/timestamps), and
`model_validate` for already typed Python values. JSON schemas are available through
each class's `model_json_schema()`. [Record fixtures](examples/records.json) freeze
IDs/time and round-trip every record type; they include an unsuccessful tool call.

| Record | References and purpose |
| --- | --- |
| Session | Fixed shared/isolated/ephemeral mode; title, archived, pinned metadata |
| Message | Session and run; verbatim text and role; tool messages require a tool-call ID |
| Run | Session, request idempotency ID, profile, optional retry-of run; scheduled/proactive runs require job and occurrence IDs |
| ModelStep | Session, run, attempt index (starts at 1), model pin, optional provider response ID, normalized content/reasoning/outcome |
| ModelRequest | Session, run, attempt index and pin; exact body/manifest artifact references, durable before transmission |
| ToolCall | Session, run, model step, provider tool-call ID, name, JSON arguments |
| ToolReceipt | Session, run, internal tool-call ID even on failure; status, result, failure, effect certainty |
| Job | Profile, task, schedule string/timezone, bound session or ephemeral target; disabled initially |
| Occurrence | Job, UTC due time, optional admitted run, operational state and reason |
| Delivery | Session, run, message; independent publication lifecycle |
| MemoryCommit | Session, run, optional provider commit ID; independent extraction lifecycle |
| CompactionBoundary | Session, creating run, through-message, summary-message, ordered original source message IDs |

Request IDs, run IDs, internal call IDs, provider response IDs, and provider
tool-call IDs occupy distinct roles. A retry creates a new run linked by
`retry_of`; it does not change the old terminal record. Provider IDs are bounded
opaque strings and must never form local paths. Request IDs are generated by the
admission boundary, separate from any future HTTP idempotency header mapping.

Records validate local shape. The Phase 3 store enforces referential integrity
and same-session/run relationships; arbitrary unverified IDs are not permission
to read another session. Session mode freezes at first admission. Scheduled and
proactive run lineage is mandatory and cannot be relabeled by the model. The
job's `origin` records who defined it; a scheduled occurrence/run's origin records
the execution trigger. Proactive work cannot create descendants or manage wakes;
Phase 5/9 services enforce this independently of serialized records. Schedule
syntax, timezone existence, and occurrence claiming are Phase 9 responsibilities.

## Lifecycle and errors

`Run.transition` returns a validated new snapshot and rejects duplicate terminal
attempts, including a repeated transition to the same state. State change and
persistence must share the Phase 3/6 admission transaction/outbox boundary.

| Current | Next |
| --- | --- |
| queued | running, cancelled, interrupted, failed |
| running | completed, failed, cancelled, interrupted |
| completed / failed / cancelled / interrupted | none |

Running requires a start time. Every terminal snapshot requires an end time;
queued failures/cancellations need no start time. Time cannot move backwards.
Waiting for inference, model generation, or a tool is progress within `running`.
An outcome `reason` is separate from state. `completed` can represent an evaluated
proactive no-action result; publication is not required.

Delivery: `pending -> sending | cancelled`, then
`sending -> delivered | failed | uncertain`. Each resulting terminal state is
immutable. Uncertain delivery cannot be retried as a new send without explicit
reconciliation/provider idempotency. Phase 7 memory extends its initial skeleton:
`pending -> running -> accepted -> completed | failed`, with `ambiguous` for lost
submission acceptance and explicit operator reconciliation to attach a verified
provider task. Pending preflight and accepted observation retain bounded persisted
backoff. No ambiguous submission is replayed. A completed reply can retain pending
delivery or extraction; neither lifecycle rewrites the run outcome. See the
[memory contract](memory.md) for eligibility, caps and recovery.

Tool receipts distinguish `succeeded`, `failed`, `denied`, `cancelled`, and
`uncertain`; non-success requires failure details. Effect certainty is separately
`none`, `confirmed`, or `uncertain`. Failed/cancelled work can still have a confirmed
effect. Denial requires no effect. Uncertain status/effect must agree. Never retry
an uncertain non-idempotent operation blindly.

`Failure` carries a stable `ErrorCode` and an inspectable message, never an SDK
exception object. Messages entering operational output must already be safe.

| Codes | Meaning / consumer action |
| --- | --- |
| invalid_input, configuration | Reject at the boundary; correct the input/configuration |
| budget_exceeded | Stop within admitted limits; a new run may receive new limits |
| model_unavailable, model_mismatch, invalid_model_response | Preserve request evidence; no silent model substitution or success |
| tool_denied, tool_failed | Preserve call ID and receipt; denial occurs before effect |
| timeout, cancelled, process_interrupted | Preserve what ran; timeout alone does not prove no effect |
| effect_uncertain | Inspect/reconcile before any retry |
| memory_unavailable | Label degradation or fail if memory is required |
| storage_failed, corruption | Do not acknowledge missing durability; surface and reconcile |

`InvalidTransition`, `ConfigError`, `OwnershipError`, and `LifecycleError` are local
boundary exceptions. They are not additional run states. Recovery explains an old
outcome with a new event rather than rewriting it. Queued recovery policy remains
with Phase 6.

## Events, replay, and snapshots

The [event examples](examples/events.jsonl) use `DurableEvent`: version, stable
event ID, run ID, session ID, sequence, UTC timestamp, type, and JSON payload.
Ordering is **per session**, across all of its runs, starting at 1. There is no
global ordering, and timestamp equality does not imply sequence equality.
Replay cursor is `(session_id, sequence)` with exclusive-after reads. Phase 3 owns
durable sequence allocation and event IDs through the transactional outbox.

Types are `run.admitted`, `run.started`, `run.terminal`, `message.appended`,
`model.recorded`, `tool.intent`, `tool.receipt`, `memory.changed`,
`delivery.changed`, `compaction.recorded`, and `recovery.noted`. Payloads carry the changed record or its immutable evidence
reference; the examples use compact changed fields. No arbitrary SDK object enters
payloads. The Phase 3 [storage contract](storage.md) defines concrete evidence references.

One logical terminal event is allowed per run. Replaying the same outbox ID with
identical content is idempotent; the same ID with different content is corruption.
A second terminal attempt fails rather than allocating another terminal event.
These constraints are enforced by the Phase 3 store; the Phase 2 values alone do
not persist events. A recovery event has a new ID/type and cannot impersonate terminal success.

`TokenPreview` has a run ID and text, no durable sequence, and can be dropped.
Consumers obtain the authoritative session/run snapshot plus its session high-water
sequence from the state service, then replay strictly after that cursor. Phase 10
exposes this through HTTP. Snapshot and high-water acquisition must be consistent;
if replay is unavailable/corrupt, refresh the snapshot and report the condition.
Consumers deduplicate by event ID. Reconnecting never requires every token preview
to have survived.

## Configuration and effective authority

Copy [config.example.toml](../../config.example.toml) to the default operator file
`~/.config/sola/config.toml` or select an edited copy with `--config`. Set the model
pin and workspace roots before use; the example records built-in effective
defaults. See the [configuration reference](../config.md) for every setting.
All paths are relative to the config file's directory;
`~` expands explicitly. Check resolves existing directories/fragments without
creating them, constructing the server, opening databases, acquiring ownership,
or contacting any service. An empty TOML parses for initialization but cannot
resolve a runnable profile without an existing workspace root and explicit model
pin. Loaded/granted tools start empty. Phase 5 adds exact configured module loading
and `*`/`?` expansion against explicitly loaded names; no automatic discovery.

`[defaults]` supplies workspace roots, grants (`tools`), memory mode, fragments,
and budgets. `[profiles.NAME]` inherits `default`, or a
named parent through `extends`. Cycles, unknown parents, and use of the reserved
`default` profile name fail resolution. An explicit empty list clears inheritance;
omission inherits. Child roots must be within canonical inherited roots; tool
grants must be subsets; budgets cannot increase. Fragments are
operator-selected replacement lists, preserve order, and must name existing files.
Unknown keys and invalid types fail even in unused profile tables; semantic
inheritance/root validation applies to the selected profile and its ancestors.

Effective tools are `loaded_tools ∩ granted_tools`. Loading alone grants nothing.
Workspace roots and tool grants are the access controls; there are no separate
resource or effect permissions. Old `resources` and `effects` keys are rejected as
unknown settings. Session isolation, origin rules, budgets, and protected-path
checks still apply at their service boundaries. Memory is `off`,
`optional`, or `required`; profiles cannot enable an inherited `off`. Isolated and
ephemeral sessions force `off`. Required memory changes failure policy, not scope.

`EffectiveProfile` is frozen with immutable collections and includes the pin,
endpoint, credential environment reference, roots, loaded/granted/effective tools,
mode, fragments, budgets, and per-field sources. It records
paths, not fragment bytes; Phase 4 hashes/freezes exact fragment bytes at request
assembly. No later edit can change an existing snapshot. Dispatch intersects
current grants and budgets with the admitted profile via `restrict_to_admission`:
revocations apply, additional grants cannot widen the run, roots intersect, and
identity/endpoint/data-directory changes require new admission. The admitted origin,
session mode, and fragments remain fixed. Job-specific profiles use the same
subset/ceiling rules; Phase 5 dispatch enforces them against durable admission evidence.

Model credentials use only `model.api_key_env`, never a literal TOML key value.
Explain replaces the reference with `<redacted>` and never reads the environment
value. Model endpoint URLs reject userinfo, query strings, and fragments. Config
errors report field locations without echoing raw input. Explanation sources
identify the setting, never the secret's environment variable name. This is
operational redaction, not a content scrubber for private conversation evidence.

`sola check --config PATH --profile NAME --explain` emits safe values and sources
as JSON. `runtime_configured` means local validation passed, not that the pin or
remote services were verified. Invalid explicit/existing config exits 2. A missing
default config reports an unconfigured installation and exits 0 for clean-install
checks. The four public commands remain `serve`, `check`, `prompt`, and `search`.

## Budgets

| Setting | Interactive default | Proactive default ceiling | Allowed operator range / unit |
| --- | --- | --- | --- |
| model_calls | 16 | 8 | 1–256 provider attempts per run, including retries |
| tool_calls | 32 | 12 | 1–256 dispatch attempts per run, including denials |
| active_seconds | 900 | 600 | 1–86400 monotonic elapsed seconds after run start, including inference waits; excludes queued admission time |
| output_tokens | 4096 | inherited | 1–32768 maximum requested completion tokens per provider call |
| tool_result_bytes | 65536 | inherited | 1–1048576 UTF-8 bytes per model-facing tool result; full evidence uses separately bounded artifacts in Phase 5 |
| tool_timeout_seconds | 60 | inherited | 1–3600 elapsed seconds per tool attempt |

Resolution: builtins -> operator defaults -> successive child profiles. Children
only lower values. Proactive runs then take the minimum with built-in proactive
ceilings overlaid by `[proactive_budgets]`. Operator overrides can tune proactive
ceilings up or down within the numeric ranges, still capped by the selected
profile. Dispatch takes the minimum of admission and current limits. Enforcement
and accounting are Phase 5/6/9 work. Wake rates, quiet hours, durable counters, and
enabled switches remain Phase 9 settings; no wakes run here.

## Startup, shutdown, and ownership

`compose(profile, resources=(...))` constructs one `ApplicationContext`, one
`asyncio.Semaphore(1)`, and one lifecycle lock. It starts nothing. Resources are
explicit objects with async `start`/`stop`; no service locator, import discovery,
HTTP dependency container, or extra worker is involved. Current composition supplies the Phase 3 store first, without live external clients. Later phases supply resources in dependency order:

| Owner/resource | Startup dependency / shutdown obligation |
| --- | --- |
| Data-directory lock | Acquired first; released last only after successful cleanup |
| state.db and search.db stores | Open before workers/subscriptions; close after their users |
| Model client / shared semaphore | One app-lifetime client; every model consumer uses this same permit |
| Memory client and observers | Stop new extraction, drain/cancel observers before closing client/stores |
| Event subscriptions | Close/unsubscribe and release queues on stop |
| Worker and scheduler | Stop admission/wakes first; cancel/drain work before clients/stores close |

FastAPI lifespan calls context start/stop and holds the context only at the HTTP
boundary. Resources start in the supplied order, stop in reverse. Register a
resource for cleanup *before* its start so partially opened resources also close.
A failed start preserves the startup error and, if needed, cleanup errors.
Repeated/concurrent starts or stops are serialized and idempotent; a cleanly
stopped context can restart on its single owning event loop.

Shutdown has a total deadline (`shutdown_timeout_seconds`: default 5, range 1–60).
Close failures still attempt the remaining resources. A timeout cancels the cleanup
task and returns an inspectable error without waiting forever for cancellation.
On any failed/uncertain cleanup the context becomes `failed`, retains ownership,
and refuses restart. Stop can be retried after the prior cleanup task settles;
resource stop implementations must be idempotent. Retaining the lock prevents
another runtime from accessing potentially live resources. Process exit releases
the OS lock; Phase 3/6 recovery still determines interrupted/uncertain work.

The data directory uses a persistent `.owner.lock` inode and nonblocking advisory
`flock` on a descriptor with close-on-exec and no-follow. Second owners fail within
one process or across processes. Never unlink the lock file on shutdown: replacing
its inode would allow split ownership. New directories/files use private modes;
existing directory permissions and content are preserved. This targets the local
macOS/Linux filesystem boundary, not network filesystems or malicious operator
code ignoring advisory locks.


Phase 6 composition now registers Store, ModelAdapter, supplied resources, then
RunLoop in dependency order. The RunLoop closes first and owns its queue coordinator
and bounded active run tasks. Accepted queued work may contact oMLX on startup;
otherwise startup still does not probe the service. Public headless admission,
waiting/cancellation, concurrency and recovery are specified in the
[run contract](run-loop.md). Scheduled admission remains Phase 9.
